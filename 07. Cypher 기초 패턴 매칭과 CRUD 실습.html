    Cypher 기초 실습: 패턴 매칭과 CRUD

    강의의 "한글 요리 그래프" 하나로 조회 → 생성 → 수정 → 삭제 → 집계 → 함수·파라미터까지 차례로 실행하는 실습입니다. 강의 슬라이드의 질의를 그대로 실행해 같은 결과가 나오는지 확인하고, 데이터를 늘려 가며 직접 질의를 작성합니다.

    소요 시간 약 100~120분대응 강의 8. Cypher 기초 — 패턴 매칭과 CRUD준비물 비어 있는 AuraDB 인스턴스(Free 가능)표기 라벨·관계 타입·속성·변수는 한글, 예약어만 영문검증 예상 결과가 있는 쿼리를 실제 AuraDB Free 인스턴스(Cypher 25)에서 실행해 확인 (2026-11-14)
    사람요리기준 그래프 노드 4 · 관계 4확장 후 노드 11 · 관계 14
    STEP 00

    시작 전 준비

    목표 실습 전용 인스턴스가 비어 있는지 확인합니다.

    00-1 · 데이터 개수 확인
    MATCH (n) RETURN count(n) AS 노드수;
    예상 결과

    노드수 = 0. 이전 실습 데이터가 남아 있으면 MATCH (n) DETACH DELETE n;으로 비우고, SHOW CONSTRAINTS;로 남은 제약조건이 있으면 DROP CONSTRAINT 이름;으로 지운 뒤 시작하세요.

    주의 마지막 STEP에서 모든 노드를 지웁니다. 실습 전용 인스턴스에서만 진행하세요.
    STEP 01

    패턴 문법과 SQL 대응

    목표 괄호는 노드, 화살표는 관계입니다. 질의문이 곧 그래프 모양이라는 점과, SQL의 어느 절이 Cypher의 어느 절에 대응하는지 먼저 정리합니다.

    01-1 · 전체 형태 (실행하지 않고 읽기)
    // (변수:라벨 {속성})-[변수:타입 {속성}]->(변수:라벨 {속성})
//
// (요리사:사람 {이름:'김철수'})-[:개발]->(요리:요리)
//   └ 노드 패턴                 └ 관계 패턴   └ 노드 패턴
//
// (n)        라벨·속성 생략 → 모든 노드
// (:요리)    변수 생략 → 라벨만
// -[:개발]-  방향 생략 → 양방향 탐색
    SQL과 Cypher 대응
    SQLCypher의미
    SELECTRETURN출력 항목 지정
    FROM 테이블MATCH (변수:라벨)조회 대상 지정
    WHEREWHERE필터 조건 (이름도 역할도 같음)
    JOIN-[:관계타입]->별도 구문 없이 패턴에 내장
    INSERTCREATE / MERGE생성
    UPDATESET수정
    GROUP BY(없음)집계 함수가 아닌 항목이 자동으로 그룹 키
    01-2 · 데이터 없이도 실행되는 RETURN
    RETURN '안녕하세요' AS 인사, 1 + 2 AS 합, ['한식', '분식'] AS 종류목록;
    예상 결과

    한 행: 안녕하세요 · 3 · ["한식", "분식"]

    STEP 02

    제약조건과 기준 그래프 만들기

    목표 고유 제약조건을 먼저 만들고, MERGE로 노드 4개 · 관계 4개짜리 기준 그래프를 적재합니다. 이후 모든 예제가 이 그래프에서 출발합니다.

    02-1 · 제약조건 먼저
    CREATE CONSTRAINT 요리_고유 IF NOT EXISTS
FOR (요리:요리) REQUIRE 요리.요리명 IS UNIQUE;

CREATE CONSTRAINT 사람_고유 IF NOT EXISTS
FOR (사람:사람) REQUIRE 사람.이름 IS UNIQUE;
    예상 결과

    문장 2개 성공. IF NOT EXISTS 덕분에 다시 실행해도 오류가 나지 않습니다. 고유 제약조건은 뒤에 나올 MERGE가 중복 없이 동작하는 전제입니다.

    02-2 · 노드: 고유 키로 MERGE, 나머지는 SET
    MERGE (철수:사람 {이름: '김철수'}) SET 철수.나이 = 45
MERGE (영희:사람 {이름: '이영희'}) SET 영희.나이 = 38
MERGE (찌개:요리 {요리명: '김치찌개'}) SET 찌개.등록연도 = 2019, 찌개.종류 = '한식'
MERGE (떡볶이:요리 {요리명: '떡볶이'}) SET 떡볶이.등록연도 = 2003, 떡볶이.종류 = '분식'
MERGE (철수)-[:개발]->(찌개)
MERGE (철수)-[:개발]->(떡볶이)
MERGE (영희)-[좋아함1:좋아함]->(찌개)   SET 좋아함1.별점 = 5
MERGE (영희)-[좋아함2:좋아함]->(떡볶이) SET 좋아함2.별점 = 4;
    02-3 · 적재 검증
    MATCH (n) WITH count(n) AS 노드수
MATCH ()-[r]->()
RETURN 노드수, count(r) AS 관계수;
    예상 결과

    노드수 4 · 관계수 4. 02-2를 한 번 더 실행한 뒤 02-3을 다시 실행해 보세요. 숫자가 그대로면 적재 스크립트가 멱등(여러 번 실행해도 결과가 같음)하다는 뜻입니다.

    02-4 · 전체 그래프 보기
    MATCH (a)-[r]->(b) RETURN a, r, b;
    STEP 03

    조회 기본: MATCH · WHERE · RETURN

    목표 라벨과 속성으로 노드를 찾고, 관계를 따라 이웃을 조회하고, 조건으로 거릅니다.

    03-1 · 라벨과 속성으로 단일 노드 조회
    MATCH (사람:사람 {이름:'김철수'})
RETURN 사람;
    예상 결과

    노드 1개(이름: 김철수, 나이: 45). SQL로는 SELECT * FROM 사람 WHERE 이름 = '김철수'입니다.

    03-2 · 관계를 따라 이웃 조회
    MATCH (요리사:사람 {이름:'김철수'})-[:개발]->(요리:요리)
RETURN 요리.요리명 AS 요리명, 요리.등록연도 AS 등록연도
ORDER BY 요리.등록연도 DESC;
    예상 결과
    요리명등록연도
    김치찌개2019
    떡볶이2003

    SQL이라면 사람·개발·요리 세 테이블을 JOIN해야 하는 질의가 화살표 하나로 끝납니다.

    03-3 · 다중 조건 필터와 DISTINCT
    MATCH (손님:사람)-[:좋아함]->(요리:요리)
WHERE 요리.등록연도 >= 2010 AND 요리.종류 = '한식'
RETURN DISTINCT 손님.이름 AS 손님;
    예상 결과

    이영희 (1행). 이영희 → 떡볶이(2003 · 분식)는 조건에서 탈락하고 김치찌개(2019 · 한식)만 통과합니다.

    03-4 · 관계 속성으로 거르기
    MATCH (손님:사람)-[좋아함:좋아함]->(요리:요리)
WHERE 좋아함.별점 >= 5
RETURN 손님.이름 AS 손님, 요리.요리명 AS 요리명, 좋아함.별점 AS 별점;
    예상 결과

    이영희 · 김치찌개 · 5

    03-5 · ORDER BY · SKIP · LIMIT (페이지 단위 조회)
    MATCH (요리:요리)
RETURN 요리.요리명 AS 요리명, 요리.등록연도 AS 등록연도
ORDER BY 등록연도
SKIP 1 LIMIT 1;
    예상 결과

    김치찌개 · 2019. 등록연도 오름차순으로 첫 행(떡볶이)을 건너뛰고 한 행만 가져옵니다. SKIP 0 LIMIT 10이 1페이지, SKIP 10 LIMIT 10이 2페이지입니다.

    STEP 04

    조회 심화: OPTIONAL MATCH · WHERE NOT · 문자열

    목표 매칭되지 않아도 행을 남기는 선택 매칭, 관계가 없는 노드 찾기, 문자열 조건을 실행합니다.

    04-1 · 선택 매칭 — OPTIONAL MATCH
    // 매칭되지 않으면 null (SQL의 LEFT JOIN과 유사)
MATCH (요리:요리)
OPTIONAL MATCH (요리사:사람)-[:개발]->(요리)
RETURN 요리.요리명 AS 요리명, 요리사.이름 AS 요리사;
    예상 결과

    김치찌개 · 김철수 / 떡볶이 · 김철수. 지금은 모든 요리에 개발자가 있어서 MATCH와 결과가 같습니다. 개발자가 없는 요리가 생겼을 때의 차이는 STEP 07-5에서 다시 확인합니다.

    04-2 · 관계가 없는 노드 찾기 — WHERE NOT 패턴
    MATCH (사람:사람)
WHERE NOT (사람)-[:개발]->(:요리)
RETURN 사람.이름 AS 개발한요리없음;
    예상 결과

    이영희. SQL이라면 서브쿼리와 NOT EXISTS가 필요한 질의가 패턴 한 줄입니다.

    04-3 · 문자열 조건 — CONTAINS · STARTS WITH
    MATCH (요리:요리)
WHERE 요리.요리명 CONTAINS '떡'
   OR 요리.요리명 STARTS WITH '김'
RETURN 요리.요리명;
    예상 결과

    떡볶이 · 김치찌개 (2행, 순서는 다를 수 있음). OR이므로 하나만 맞아도 통과합니다. ENDS WITH '찌개'도 같은 방식으로 씁니다.

    STEP 05

    생성: CREATE와 MERGE

    목표 CREATE는 무조건 새로 만들고 MERGE는 있으면 찾고 없으면 만듭니다. 차이를 실행 횟수로 확인하고, 관계를 만들 때의 올바른 순서를 익힙니다.

    05-1 · CREATE는 실행할 때마다 생긴다 (두 번 실행하세요)
    CREATE (:메모 {내용: '연습'});
    05-2 · MERGE는 몇 번 실행해도 하나 (두 번 실행하세요)
    MERGE (:메모 {내용: '병합'});
    05-3 · 개수 확인 후 정리
    MATCH (메모:메모)
RETURN 메모.내용 AS 내용, count(*) AS 개수;
    예상 결과

    연습 2 · 병합 1. CREATE는 실행한 횟수만큼, MERGE는 하나만 생겼습니다.

    05-3b · 연습용 메모 지우기 (반드시 실행)
    MATCH (메모:메모) DELETE 메모;
    05-4 · 고유 제약조건이 있으면 CREATE 중복은 거부된다 (오류가 나는 것이 정상)
    CREATE (:사람 {이름: '김철수', 나이: 99});
    예상 결과

    22N80: Data exception - index entry conflict 오류. 이미 같은 이름의 사람 노드가 있다는 제약조건 위반입니다. 잘못된 데이터가 들어오는 것을 데이터베이스가 막아 줍니다.

    05-5 · MERGE — 고유 키 기준 멱등 처리 (두 번 실행하세요)
    MERGE (사람:사람 {이름:'박민수'})
ON CREATE SET 사람.나이 = 41,
              사람.등록일시 = datetime()
ON MATCH  SET 사람.수정일시 = datetime()
RETURN 사람.이름 AS 이름, 사람.나이 AS 나이,
       사람.등록일시 IS NOT NULL AS 등록됨,
       사람.수정일시 IS NOT NULL AS 수정됨;
    예상 결과

    첫 실행: 박민수 · 41 · true · false (없어서 생성 → ON CREATE). 두 번째 실행: 박민수 · 41 · true · true (있어서 매칭 → ON MATCH). 몇 번 실행해도 박민수 노드는 1개입니다.

    관계 생성의 올바른 순서

    05-6 · 잘못된 예: 노드까지 함께 MERGE (오류가 나는 것이 정상)
    MERGE (사람:사람 {이름:'박민수'})
      -[:개발]->(요리:요리 {요리명:'된장찌개'});
    예상 결과

    22N80: … index entry conflict 제약조건 위반 오류. MERGE는 패턴 전체가 있는지 봅니다. "박민수가 된장찌개를 개발했다"는 패턴이 통째로 없으니 전부 새로 만들려 하고, 이미 있는 박민수와 충돌합니다. 제약조건이 없었다면 오류 없이 박민수 노드가 하나 더 생겼을 것입니다.

    05-7 · 올바른 예: 노드를 먼저 확보하고 관계만 MERGE
    MERGE (사람:사람 {이름:'박민수'})
MERGE (요리:요리 {요리명:'된장찌개'})
  ON CREATE SET 요리.등록연도 = 2003
MERGE (사람)-[관계:개발]->(요리)
  ON CREATE SET 관계.등록일시 = datetime()
RETURN 사람.이름 AS 요리사, 요리.요리명 AS 요리명;
    05-8 · 두 번 실행한 뒤 검증
    MATCH (n) WITH count(n) AS 노드수
MATCH ()-[r]->()
RETURN 노드수, count(r) AS 관계수;
    예상 결과

    노드수 6 · 관계수 5. 05-7을 여러 번 실행해도 이 숫자가 유지되어야 합니다. 적재 스크립트는 두 번 실행해 데이터가 늘지 않는지 반드시 검증합니다.

    CREATE vs MERGE
    항목CREATEMERGE
    동작무조건 새로 생성존재하면 매칭, 없으면 생성
    중복같은 데이터가 중복 생성됨중복 방지
    성능빠름패턴 조회 비용이 추가됨
    필수 조건없음매칭 기준 속성에 고유 제약조건
    용도최초 적재, 중복이 없음이 보장된 경우증분 적재, 재실행 가능한 스크립트
    STEP 06

    수정: SET과 REMOVE

    목표 속성을 추가·변경하고, 맵으로 일괄 갱신하고, 라벨과 속성을 제거합니다.

    06-1 · 속성 변경 / 추가
    MATCH (사람:사람 {이름:'김철수'})
SET 사람.지역 = '서울', 사람.단골 = true
RETURN properties(사람) AS 속성;
    예상 결과

    {이름: "김철수", 나이: 45, 지역: "서울", 단골: true}(표시 순서는 다를 수 있음). 없는 속성은 추가되고 있는 속성은 바뀝니다.

    06-2 · 맵으로 일괄 갱신: += 는 병합
    MATCH (요리:요리 {요리명:'김치찌개'})
SET 요리 += {조리시간:20, 수정일시:datetime()}
RETURN keys(요리) AS 속성키;
    예상 결과

    요리명 · 등록연도 · 종류 · 조리시간 · 수정일시 (5개, 순서는 다를 수 있음). 기존 등록연도와 종류는 그대로 남습니다.

    06-3 · = 는 전체 교체 (기존 속성이 사라지는 것을 확인)
    MATCH (요리:요리 {요리명:'된장찌개'})
SET 요리 = {요리명:'된장찌개', 조리시간:25}
RETURN properties(요리) AS 속성;
    예상 결과

    {요리명: "된장찌개", 조리시간: 25}. 등록연도가 사라졌습니다. +=를 쓰려다 =를 쓰면 기존 속성이 모두 지워집니다.

    06-4 · 되돌리기
    MATCH (요리:요리 {요리명:'된장찌개'})
SET 요리.등록연도 = 2003
REMOVE 요리.조리시간
RETURN properties(요리) AS 속성;
    06-5 · 라벨 추가 / 제거
    MATCH (사람:사람 {이름:'이영희'}) SET 사람:손님
RETURN labels(사람) AS 라벨;
    예상 결과

    ["사람", "손님"]. 이영희는 사람이면서 손님입니다. MATCH (손님:손님) RETURN 손님.이름;으로 조회해 보세요.

    06-6 · 라벨 제거, 속성 제거
    MATCH (사람:사람 {이름:'이영희'}) REMOVE 사람:손님;
MATCH (사람:사람 {이름:'김철수'}) REMOVE 사람.단골;
    06-7 · 확인
    MATCH (사람:사람)
RETURN 사람.이름 AS 이름, labels(사람) AS 라벨, 사람.지역 AS 지역, 사람.단골 AS 단골
ORDER BY 이름;
    예상 결과
    이름라벨지역단골
    김철수["사람"]서울null
    박민수["사람"]nullnull
    이영희["사람"]nullnull

    없는 속성을 조회하면 오류가 아니라 null이 나옵니다.

    STEP 07

    삭제: DELETE와 DETACH DELETE

    목표 관계가 남아 있는 노드는 지울 수 없다는 규칙을 확인하고, 두 가지 방법으로 삭제합니다.

    07-1 · 그냥 지우기 (오류가 나는 것이 정상)
    MATCH (사람:사람 {이름:'박민수'})
DELETE 사람;
    예상 결과

    G1001: Dependent object error - edges still exist 오류. 관계가 남아 있어 삭제할 수 없습니다. 그래프에 끊어진 관계가 남지 않도록 보호하는 규칙입니다.

    07-2 · 방법 1: 관계 삭제 → 노드 삭제
    MATCH (:사람 {이름:'박민수'})-[관계:개발]->()
DELETE 관계;

MATCH (사람:사람 {이름:'박민수'})
DELETE 사람;
    예상 결과

    관계 1개 삭제, 이어서 노드 1개 삭제.

    07-3 · 방법 2: DETACH DELETE (연습용 노드로 확인)
    MERGE (사람:사람 {이름:'임시요리사'})
MERGE (요리:요리 {요리명:'된장찌개'})
MERGE (사람)-[:개발]->(요리);

MATCH (사람:사람 {이름:'임시요리사'})
DETACH DELETE 사람;
    예상 결과

    두 번째 문장에서 노드 1개와 관계 1개가 한 번에 삭제됩니다. DETACH DELETE는 관계까지 함께 지우므로 두 단계를 한 문장으로 줄입니다.

    07-4 · 현재 상태 확인
    MATCH (n) WITH count(n) AS 노드수
MATCH ()-[r]->()
RETURN 노드수, count(r) AS 관계수;
    예상 결과

    노드수 5 (사람 2 · 요리 3) · 관계수 4. 된장찌개는 개발자 없이 남았습니다.

    07-5 · OPTIONAL MATCH 다시 보기
    MATCH (요리:요리)
OPTIONAL MATCH (요리사:사람)-[:개발]->(요리)
RETURN 요리.요리명 AS 요리명, 요리사.이름 AS 요리사
ORDER BY 요리명;
    예상 결과
    요리명요리사
    김치찌개김철수
    된장찌개null
    떡볶이김철수

    OPTIONAL MATCH를 MATCH로 바꿔 실행하면 된장찌개 행이 사라집니다. 직접 바꿔서 확인하세요.

    STEP 08

    집계 연습용으로 그래프 넓히기

    목표 집계와 파이프라인을 연습하기에는 데이터가 적습니다. UNWIND와 MERGE로 사람과 요리를 추가합니다.

    08-1 · 사람과 요리 추가
    UNWIND [
  {이름: '박민수', 나이: 41},
  {이름: '최지우', 나이: 29},
  {이름: '정하늘', 나이: 52}

MERGE (사람:사람 {이름: 행.이름})
SET 사람.나이 = 행.나이;

UNWIND [

  {요리명: '비빔밥',   등록연도: 1997, 종류: '한식'},
  {요리명: '라면',     등록연도: 2021, 종류: '분식'},
  {요리명: '잡채',     등록연도: 2012, 종류: '한식'}
] AS 행
MERGE (요리:요리 {요리명: 행.요리명})
SET 요리.등록연도 = 행.등록연도, 요리.종류 = 행.종류;
    08-2 · 개발과 좋아함 추가

  ['박민수', '된장찌개'], ['박민수', '비빔밥'], ['최지우', '라면']

    STEP 09

    집계: count · collect · 통계

    목표 그룹별로 세고 모읍니다. Cypher에는 GROUP BY가 없고, RETURN에서 집계 함수에 들어가지 않은 항목이 자동으로 그룹 키가 됩니다.

    09-1 · 요리사별 개발한 요리 수
    MATCH (요리사:사람)-[:개발]->(요리:요리)
RETURN 요리사.이름 AS 요리사, count(요리) AS 개발수
ORDER BY 개발수 DESC, 요리사
LIMIT 10;
    예상 결과

    김철수 2 · 박민수 2 · 최지우 1. 요리사가 자동 그룹 키입니다.

    09-2 · 목록으로 수집
    MATCH (요리사:사람 {이름:'김철수'})-[:개발]->(요리:요리)
RETURN 요리사.이름 AS 요리사,
       collect(요리.요리명) AS 요리목록;
    예상 결과

    김철수 · ["김치찌개", "떡볶이"] (목록 안의 순서는 다를 수 있음). 두 요리가 리스트 하나로 반환됩니다.

    09-3 · 통계 집계
    MATCH (요리:요리)
RETURN count(요리) AS 요리수,
       min(요리.등록연도) AS 최초,
       max(요리.등록연도) AS 최근,
       round(avg(요리.등록연도), 1) AS 평균등록연도;
    예상 결과

    요리수 6 · 최초 1997 · 최근 2021 · 평균등록연도 2009.2

    09-4 · 종류별 요리 수와 목록
    MATCH (요리:요리)
RETURN 요리.종류 AS 종류, count(*) AS 요리수, collect(요리.요리명) AS 요리들
ORDER BY 요리수 DESC;
    예상 결과

    한식 4 [김치찌개, 된장찌개, 비빔밥, 잡채] · 분식 2 [떡볶이, 라면]

OPTIONAL MATCH (요리)<-[좋아함:좋아함]-(:사람)
RETURN 요리.요리명 AS 요리명, count(좋아함) AS 좋아하는사람수, avg(좋아함.별점) AS 평균별점

    김치찌개34.0

    STEP 10

    WITH: 질의 파이프라인

    목표 집계 결과를 다시 거르거나 다음 패턴으로 넘길 때 WITH를 씁니다. MATCH로 찾고 → WITH로 집계해 넘기고 → WHERE로 거르고 → 다시 MATCH로 확장하는 흐름입니다.

    10-1 · 집계 결과에 WHERE를 직접 쓰면 (오류가 나는 것이 정상)
    MATCH (요리사:사람)-[:개발]->(요리:요리)
WHERE count(요리) >= 2
RETURN 요리사.이름;
    예상 결과

    42I24: … invalid use of aggregate function 오류. 집계 함수는 WHERE에서 쓸 수 없습니다.

    10-2 · WITH로 집계한 뒤 WHERE (SQL의 HAVING 역할)
    MATCH (요리사:사람)-[:개발]->(요리:요리)
WITH 요리사, count(요리) AS 개발수
WHERE 개발수 >= 2
RETURN 요리사.이름 AS 요리사, 개발수
ORDER BY 요리사;
    예상 결과

    김철수 2 · 박민수 2

    10-3 · 요리 2개 이상 개발한 요리사와 그 요리를 좋아하는 사람
    MATCH (요리사:사람)-[:개발]->(요리:요리)
WITH 요리사, count(요리) AS 개발수
WHERE 개발수 >= 2
MATCH (요리사)-[:개발]->(:요리)<-[:좋아함]-(손님:사람)
RETURN 요리사.이름 AS 요리사, 개발수,
       collect(DISTINCT 손님.이름) AS 좋아하는사람
ORDER BY 개발수 DESC, 요리사;
    예상 결과

    김철수 · 2 · [이영희, 최지우, 정하늘] / 박민수 · 2 · [정하늘, 김철수]. 목록 안의 순서는 다를 수 있습니다.

    10-4 · WITH 다음에는 명시한 변수만 살아남는다 (오류가 나는 것이 정상)
    MATCH (요리사:사람)-[:개발]->(요리:요리)
WITH 요리사, count(요리) AS 개발수
RETURN 요리사.이름, 요리.요리명;
    예상 결과

    42N62: … variable not defined 오류(Variable 요리 not defined). WITH에 적지 않은 변수는 그 뒤에서 쓸 수 없습니다.

    10-5 · WITH … ORDER BY … LIMIT으로 중간 결과 줄이기
    MATCH (요리:요리)<-[좋아함:좋아함]-(:사람)
WITH 요리, avg(좋아함.별점) AS 평균별점
ORDER BY 평균별점 DESC LIMIT 2
OPTIONAL MATCH (요리사:사람)-[:개발]->(요리)
RETURN 요리.요리명 AS 요리명, 평균별점, 요리사.이름 AS 요리사;
    예상 결과

    된장찌개 · 5.0 · 박민수 / 떡볶이 · 4.5 · 김철수. 상위 2개만 남긴 뒤에 다음 패턴을 확장하므로 뒤 단계가 처리할 행이 줄어듭니다.

    STEP 11

    함수 · CASE · 파라미터

    목표 자주 쓰는 함수와 조건 분기를 실행하고, 값을 질의문에 직접 붙이지 않고 $파라미터로 넘기는 습관을 들입니다.

    11-1 · 분류별 함수 한 번씩
    RETURN toUpper('neo4j')                       AS 대문자,
       split('김치,두부,파', ',')              AS 나누기,
       replace('김 치 찌 개', ' ', '')         AS 공백제거,
       round(3.14159, 2)                       AS 반올림,
       size(['가', '나', '다'])                AS 길이,
       head(['가', '나', '다'])                AS 첫원소,
       range(1, 5)                             AS 범위,
       coalesce(null, '기본값')                AS 널대체,
       duration.between(date('2019-01-01'), date('2026-11-14')).years AS 경과연수;
    예상 결과

    NEO4J · ["김치", "두부", "파"] · 김치찌개 · 3.14 · 3 · 가 · [1, 2, 3, 4, 5] · 기본값 · 7

    11-2 · 조건 분기 — CASE WHEN … THEN … END
    MATCH (요리:요리)
RETURN 요리.요리명 AS 요리명,
CASE
  WHEN 요리.등록연도 < 2000 THEN '2000년 이전'
  WHEN 요리.등록연도 < 2015 THEN '2000년대'
  ELSE '최근 등록'
END AS 등록시기
ORDER BY 요리.등록연도;
    예상 결과
    요리명등록시기
    비빔밥2000년 이전
    된장찌개2000년대
    떡볶이2000년대
    잡채2000년대
    김치찌개최근 등록
    라면최근 등록

    WHEN은 위에서부터 평가해 처음 맞는 값을 고릅니다. 된장찌개와 떡볶이는 등록연도가 같아 순서가 바뀔 수 있습니다.

    11-3 · CASE 결과로 집계하기
    MATCH (요리:요리)
RETURN CASE WHEN 요리.등록연도 < 2015 THEN '2015년 이전' ELSE '2015년 이후' END AS 시기,
       count(*) AS 요리수;
    예상 결과

    2015년 이전 4 · 2015년 이후 2

    값은 $파라미터로

    Query 화면에서는 :param 명령으로 파라미터를 설정합니다. 아래 두 블록을 따로 실행하세요.

    11-4 · 파라미터 설정

    11-5 · 파라미터를 사용하는 질의
    MATCH (요리사:사람 {이름: $요리사이름})
      -[:개발]->(요리:요리)
RETURN 요리.요리명 AS 요리명, 요리.등록연도 AS 등록연도
ORDER BY 요리.등록연도;
    예상 결과

    떡볶이 2003 · 김치찌개 2019. :param 요리사이름 => '박민수'로 값만 바꾸고 11-5를 그대로 다시 실행하면 비빔밥 1997 · 된장찌개 2003이 나옵니다. 질의문은 그대로이고 값만 바뀝니다.

    왜 파라미터인가 질의문이 같으면 실행 계획을 다시 세우지 않아 빨라지고, 문자열을 이어 붙이지 않으므로 주입 공격을 막습니다. 드라이버로 애플리케이션을 연동할 때 다시 나옵니다. 11-4를 실행하면 "1 new parameter successfully set"이 표시되고, 설정된 값은 왼쪽 패널의 Parameters 탭에서 확인할 수 있습니다.
