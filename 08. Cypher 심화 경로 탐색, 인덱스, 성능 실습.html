    STEP 01

    실습 데이터 적재 (UNWIND 배치 입력)

    목표 리스트 원소 하나가 행 하나가 되는 UNWIND로 데이터를 넣습니다. 사람에는 일부러 제약조건과 인덱스를 만들지 않습니다(STEP 08에서 비교).

    01-1 · 요리에만 고유 제약조건
    CREATE CONSTRAINT 요리_고유 IF NOT EXISTS
  FOR (요리:요리) REQUIRE 요리.요리명 IS UNIQUE;
    01-2 · 사람과 친구
    UNWIND ['김철수', '이영희', '박민수', '강민지', '최지우', '정하늘', '윤서준', '한소라'] AS 이름
MERGE (:사람 {이름: 이름});

UNWIND [
  ['김철수', '이영희'], ['김철수', '박민수'], ['이영희', '강민지'], ['박민수', '강민지'],
  ['강민지', '최지우'], ['최지우', '정하늘'], ['정하늘', '윤서준']
] AS 행
MATCH (a:사람 {이름: 행[0]})
MATCH (b:사람 {이름: 행[1]})
MERGE (a)-[:친구]->(b);
    01-3 · 요리 + 종류 + 개발
    UNWIND [
  {요리명: '김치찌개',   연도: 2019, 종류: '한식', 개발자: '김철수'},
  {요리명: '떡볶이',     연도: 2003, 종류: '분식', 개발자: '김철수'},
  {요리명: '김치볶음밥', 연도: 2015, 종류: '한식', 개발자: '김철수'},
  {요리명: '된장찌개',   연도: 2021, 종류: '한식', 개발자: '이영희'},
  {요리명: '비빔밥',     연도: 2022, 종류: '한식', 개발자: '박민수'},
  {요리명: '잡채',       연도: 2012, 종류: '한식', 개발자: '박민수'},
  {요리명: '라면',       연도: 2023, 종류: '분식', 개발자: '최지우'},
  {요리명: '부대찌개',   연도: 2020, 종류: '퓨전', 개발자: '정하늘'}
] AS 행
MATCH (개발자:사람 {이름: 행.개발자})
MERGE (요리:요리 {요리명: 행.요리명})
SET 요리.등록연도 = 행.연도
MERGE (종류:종류 {이름: 행.종류})
MERGE (요리)-[:분류]->(종류)
MERGE (개발자)-[:개발]->(요리)
RETURN count(요리) AS 요리수;

UNWIND [

  ['된장찌개', '된장', 50],  ['된장찌개', '두부', 200],
  ['김치볶음밥', '김치', 150], ['김치볶음밥', '쌀', 200],
  ['떡볶이', '떡', 300], ['떡볶이', '고추장', 60],
  ['비빔밥', '쌀', 200], ['비빔밥', '고추장', 30]
] AS 행
MATCH (요리:요리 {요리명: 행[0]})

] AS 행
MATCH (가공품:재료 {이름: 행[0]})
MATCH (원재료:재료 {이름: 행[1]})
MERGE (가공품)-[관계:재료]->(원재료)
SET 관계.분량 = 행[2];

    STEP 02

    가변 길이 경로: *최소..최대

    목표 몇 단계를 건너 이어지는 노드를 한 번에 찾습니다. 순환이 있는 그래프에서 같은 사람이 여러 번 나오는 이유도 확인합니다.

    02-1 · 1~3단계 이내로 이어지는 친구
    MATCH 경로 = (출발:사람 {이름:'김철수'})
      -[:친구*1..3]-(도착:사람)
RETURN 도착.이름 AS 사람,
       length(경로) AS 단계
ORDER BY 단계;
    예상 결과
    사람단계(설명) 어떤 경로인가
    이영희1김철수 → 이영희
    박민수1김철수 → 박민수
    강민지2김철수 → 이영희 → 강민지
    강민지2김철수 → 박민수 → 강민지
    박민수3김철수 → 이영희 → 강민지 → 박민수
    최지우3김철수 → 이영희 → 강민지 → 최지우
    이영희3김철수 → 박민수 → 강민지 → 이영희
    최지우3김철수 → 박민수 → 강민지 → 최지우

    8행(같은 단계 안의 순서는 다를 수 있음). 결과는 "사람"이 아니라 "경로"마다 한 행입니다. 김철수–이영희–강민지–박민수가 고리를 이루고 있어서, 직접 친구인 박민수가 3단계로도 한 번 더 나옵니다.

    02-2 · 사람별로 가장 가까운 단계만
    MATCH 경로 = (출발:사람 {이름:'김철수'})-[:친구*1..3]-(도착:사람)
RETURN 도착.이름 AS 사람, min(length(경로)) AS 단계
ORDER BY 단계, 사람;
    예상 결과

    박민수 1 · 이영희 1 · 강민지 2 · 최지우 3 (4행)

    02-3 · 친구의 친구 중 아직 친구가 아닌 사람
    MATCH (나:사람 {이름:'김철수'})-[:친구*2]-(후보:사람)
WHERE NOT (나)-[:친구]-(후보)
RETURN DISTINCT 후보.이름 AS 친구추천;
    예상 결과

    강민지. *2는 최소와 최대가 같아 정확히 두 단계만 따라갑니다.

    같은 관계는 한 경로에서 한 번만 Cypher는 한 패턴 안에서 같은 관계를 두 번 지나지 않습니다. 그래서 김철수 → 이영희 → 김철수처럼 되돌아오는 경로는 나오지 않습니다. 같은 노드는 다른 관계를 통해 다시 지날 수 있습니다.
    STEP 03

    정확한 단계, 여러 관계 타입, 그리고 상한

    목표 |로 관계 타입 여러 개를 동시에 지정하고, 상한 없는 탐색이 왜 위험한지 경로 수로 확인합니다.

    03-1 · 정확히 2단계 — 같은 요리로 이어진 사람
    MATCH (기준:사람 {이름:'김철수'})
      -[:개발|좋아함*2]-(동료:사람)
RETURN DISTINCT 동료.이름 AS 함께한사람;
    예상 결과

    이영희 · 강민지 · 최지우 (3행). DISTINCT를 지우면 5행입니다. 이영희는 김치찌개·떡볶이·된장찌개 세 요리로 이어져 세 번 나옵니다. 경로는 5개, 사람은 3명입니다.

    03-2 · 참고 관계를 따라 원본까지 (상한 지정)
    MATCH (요리:요리 {요리명:'김치찌개'})
      -[:참고*1..5]->(원본:요리)
RETURN DISTINCT 원본.요리명;
    예상 결과

    된장찌개

    03-3 · 라면에서 출발하면
    MATCH 경로 = (:요리 {요리명:'라면'})-[:참고*1..5]->(원본:요리)
RETURN 원본.요리명 AS 원본, length(경로) AS 단계
ORDER BY 단계;
    예상 결과

    부대찌개 1 · 김치찌개 2 · 된장찌개 3

    깊이가 늘수록 경로 수는 빠르게 늘어난다

    03-4 · 깊이별 경로 수 세기
    MATCH 경로 = (:사람 {이름:'김철수'})-[:개발|좋아함*1..6]-()
RETURN length(경로) AS 깊이, count(*) AS 경로수
ORDER BY 깊이;
    예상 결과
    깊이경로수
    14
    25
    37
    411
    514
    612

    합계 53개. 노드 16개, 관계 16개뿐인 작은 그래프인데도 이만큼 나옵니다. 여기서는 그래프가 작아 6단계에서 경로가 소진되기 시작하지만, 실제 데이터에서는 깊이마다 몇 배씩 늘어납니다.

    상한은 반드시 -[:친구*]-처럼 상한을 생략하면 그래프 전체를 순회할 수 있습니다. 큰 데이터베이스에서는 질의가 끝나지 않습니다. 항상 *1..3처럼 최대값을 쓰고, 조건은 최대한 일찍 겁니다.
    STEP 04

    최단 경로: shortestPath · allShortestPaths

    목표 두 노드 사이에서 관계 수가 가장 적은 경로를 찾습니다. 하나만 찾을 때와 모두 찾을 때를 비교합니다.

    04-1 · 두 사람 사이의 최단 경로 1개
    MATCH (시작:사람 {이름:'김철수'}),
      (도착:사람 {이름:'이영희'})
MATCH 경로 = shortestPath(
        (시작)-[:개발|좋아함*..6]-(도착))
RETURN [노드 IN nodes(경로) |
        coalesce(노드.이름, 노드.요리명)] AS 경로,
       length(경로) AS 거리;
    예상 결과

    [김철수, (요리), 이영희] · 거리 2. 가운데 요리는 김치찌개·떡볶이·된장찌개 중 하나입니다. coalesce는 사람이면 이름, 요리면 요리명처럼 있는 값을 고릅니다. Cartesian product 알림은 두 사람을 각각 하나씩 찾는 것이므로 무시해도 됩니다.

    04-2 · 최단 거리의 모든 경로
    MATCH (시작:사람 {이름:'김철수'}),
      (도착:사람 {이름:'이영희'})
MATCH 경로 = allShortestPaths(
        (시작)-[:개발|좋아함*..6]-(도착))
RETURN [노드 IN nodes(경로) | coalesce(노드.이름, 노드.요리명)] AS 경로;
    예상 결과

    3행: 김치찌개 경유 · 떡볶이 경유 · 된장찌개 경유. RETURN count(경로) AS 경로수로 바꾸면 3입니다.

    04-3 · 더 먼 두 사람
    MATCH (시작:사람 {이름:'김철수'}), (도착:사람 {이름:'윤서준'})
MATCH 경로 = shortestPath((시작)-[:개발|좋아함*..6]-(도착))
RETURN [노드 IN nodes(경로) | coalesce(노드.이름, 노드.요리명)] AS 경로,
       length(경로) AS 거리;
    예상 결과

    [김철수, 된장찌개, 최지우, 라면, 윤서준] · 거리 4

    04-4 · 관계 타입을 바꾸면 최단 경로도 바뀐다
    MATCH (시작:사람 {이름:'김철수'}), (도착:사람 {이름:'윤서준'})
MATCH 경로 = allShortestPaths((시작)-[:친구*..6]-(도착))
RETURN [노드 IN nodes(경로) | 노드.이름] AS 경로, length(경로) AS 거리;
    예상 결과

    2행, 거리 5: 김철수 → 이영희 → 강민지 → 최지우 → 정하늘 → 윤서준, 그리고 박민수를 거치는 경로.

    04-5 · 경로가 없으면
    MATCH (시작:사람 {이름:'김철수'}), (도착:사람 {이름:'한소라'})
MATCH 경로 = shortestPath((시작)-[:친구*..6]-(도착))
RETURN 경로;
    예상 결과

    결과가 비어 있습니다. 한소라는 친구 관계가 하나도 없습니다. 오류가 아니라 "경로 없음"이라는 답입니다.

    shortestPath의 기준은 관계 수 거리·비용 같은 속성(가중치)은 고려하지 않습니다. 거리: 100짜리 관계 1개와 거리: 1짜리 관계 2개가 있으면 관계 1개짜리가 선택됩니다. 가중치 최단 경로는 Graph Data Science 라이브러리의 영역입니다.
    STEP 05

    경로 객체 분해와 reduce

    목표 경로는 노드와 관계가 번갈아 이어진 하나의 값입니다. nodes(), relationships(), length()로 분해하고 reduce로 경로 위의 값을 합산합니다.

    05-1 · 경로를 세 함수로 분해
    MATCH (시작:사람 {이름:'김철수'}), (도착:사람 {이름:'윤서준'})
MATCH 경로 = shortestPath((시작)-[:개발|좋아함*..6]-(도착))
RETURN [노드 IN nodes(경로) | coalesce(노드.이름, 노드.요리명)] AS 노드목록,
       [관계 IN relationships(경로) | type(관계)] AS 관계목록,
       length(경로) AS 관계수;
    예상 결과

    노드목록 [김철수, 된장찌개, 최지우, 라면, 윤서준] · 관계목록 [좋아함, 좋아함, 개발, 좋아함] · 관계수 4. 노드는 항상 관계보다 하나 많습니다.

    05-2 · 경로 위의 분량 합산
    MATCH 경로 = (:요리 {요리명:'김치찌개'})-[:재료*1..3]->(:재료)
RETURN [노드 IN nodes(경로) | coalesce(노드.요리명, 노드.이름)] AS 재료경로,
       reduce(합계 = 0,
              관계 IN relationships(경로)
              | 합계 + 관계.분량) AS 총분량
ORDER BY 총분량 DESC;
    예상 결과
    재료경로총분량
    [김치찌개, 김치, 배추]550
    [김치찌개, 김치, 고춧가루]330
    [김치찌개, 김치]300
    [김치찌개, 두부, 콩]250
    [김치찌개, 두부]150

    reduce는 누적 변수(합계 = 0)를 들고 리스트를 하나씩 돌며 더합니다. 프로그래밍 언어의 fold와 같습니다. 김치 → 배추 경로는 0 → 300 → 550 순으로 누적됩니다.

    05-3 · 요리별로 가장 긴 재료 사슬
    MATCH 경로 = (요리:요리)-[:재료*1..3]->(:재료)
WITH 요리, reduce(합계 = 0, 관계 IN relationships(경로) | 합계 + 관계.분량) AS 총분량
RETURN 요리.요리명 AS 요리명, count(*) AS 경로수, max(총분량) AS 최대총분량
ORDER BY 최대총분량 DESC, 요리명;
    예상 결과

    김치찌개 5 · 550 / 김치볶음밥 4 · 400 / 된장찌개 4 · 300 / 떡볶이 3 · 300 / 비빔밥 3 · 200

    STEP 06

    UNWIND와 CALL 서브쿼리

    목표 리스트를 행으로 펼치는 UNWIND와, 바깥 행마다 독립적으로 실행되는 CALL 서브쿼리로 "그룹별 상위 N건"을 구합니다.

    06-1 · UNWIND — 리스트 원소 하나 = 행 하나
    UNWIND [{요리명:'된장찌개', 연도:2021}, {요리명:'비빔밥', 연도:2022}] AS 행
MERGE (요리:요리 {요리명: 행.요리명})
SET 요리.등록연도 = 행.연도
RETURN 요리.요리명 AS 요리명, 요리.등록연도 AS 등록연도;
    예상 결과

    된장찌개 2021 · 비빔밥 2022. 이미 같은 값으로 적재되어 있어 데이터는 바뀌지 않습니다. STEP 01의 적재가 모두 이 형태였습니다.

    06-2 · UNWIND로 리스트 다루기
    WITH [3, 1, 2, 3, 1] AS 숫자들
UNWIND 숫자들 AS 숫자
RETURN collect(DISTINCT 숫자) AS 중복제거, sum(숫자) AS 합계, count(*) AS 개수;
    예상 결과

    [3, 1, 2] · 10 · 5

    06-3 · 종류별 최근 등록 요리 2개씩
    MATCH (종류:종류)
CALL (종류) {
  MATCH (종류)<-[:분류]-(요리:요리)
  RETURN 요리 ORDER BY 요리.등록연도 DESC LIMIT 2
}
RETURN 종류.이름 AS 종류,
       collect(요리.요리명) AS 최근등록
ORDER BY 종류;
    예상 결과
    종류최근등록
    분식[라면, 떡볶이]
    퓨전[부대찌개]
    한식[비빔밥, 된장찌개]

    한식은 요리가 5개지만 서브쿼리 안의 LIMIT 2가 종류마다 따로 적용됩니다. SQL이라면 윈도우 함수와 순위 필터가 필요한 질의입니다.

    06-4 · 비교: 서브쿼리 없이 LIMIT을 쓰면
    MATCH (종류:종류)<-[:분류]-(요리:요리)
RETURN 종류.이름 AS 종류, 요리.요리명 AS 요리명, 요리.등록연도 AS 등록연도
ORDER BY 등록연도 DESC LIMIT 2;
    예상 결과

    분식 · 라면 · 2023 / 한식 · 비빔밥 · 2022. LIMIT이 전체 결과에 한 번만 적용되어 종류별 상위 2건이 되지 않습니다.

    CALL (변수) { … } 괄호 안에 적은 바깥 변수만 서브쿼리 안에서 쓸 수 있습니다. 예전 문법인 CALL { WITH 종류 … }도 같은 뜻이며 오래된 자료에서 자주 보입니다.
    STEP 07

    리스트·패턴 컴프리헨션과 EXISTS

    목표 별도의 MATCH와 collect 없이 RETURN 한 줄에서 리스트를 만들고, 관계가 있는지만 확인하는 EXISTS로 불필요한 확장을 막습니다.

    07-1 · 리스트 컴프리헨션: [변수 IN 리스트 WHERE 조건 | 뽑을 값]
    RETURN [x IN range(1, 6) WHERE x % 2 = 1 | x * 10] AS 홀수의열배;
    예상 결과

    [10, 30, 50]

    07-2 · 패턴 컴프리헨션: [패턴 WHERE 조건 | 뽑을 값]
    MATCH (요리사:사람 {이름:'김철수'})
RETURN 요리사.이름 AS 요리사,
       [(요리사)-[:개발]->(요리:요리)
        WHERE 요리.등록연도 > 2010 | 요리.요리명] AS 최근등록;
    예상 결과

    김철수 · [김치찌개, 김치볶음밥] (목록 안의 순서는 다를 수 있음). 2003년 등록인 떡볶이는 빠집니다.

    07-3 · 사람마다 개발 목록과 좋아함 목록을 한 번에
    MATCH (사람:사람)
RETURN 사람.이름 AS 이름,
       [(사람)-[:개발]->(요리) | 요리.요리명]   AS 개발,
       [(사람)-[:좋아함]->(요리) | 요리.요리명] AS 좋아함
ORDER BY 이름;
    예상 결과

    8행. 강민지는 개발 [], 좋아함 [김치찌개]. 패턴이 하나도 맞지 않으면 행이 사라지는 대신 빈 리스트가 됩니다. MATCH 두 개로 쓰면 두 목록이 곱해져 행이 늘어나는데, 컴프리헨션은 그렇지 않습니다.

    EXISTS — 있는지만 본다

    07-4 · MATCH로 확장하면 요리 수만큼 행이 늘어난다
    MATCH (사람:사람)-[:개발]->(:요리)
RETURN 사람.이름 AS 요리사;
    예상 결과

    8행. 김철수 3번, 박민수 2번, 이영희·최지우·정하늘 1번씩. 요리사 목록을 얻으려면 DISTINCT가 더 필요합니다.

    07-5 · EXISTS로 존재만 검사
    MATCH (사람:사람)
WHERE EXISTS { (사람)-[:개발]->(:요리) }
RETURN 사람.이름 AS 요리사;
    예상 결과

    5행: 김철수 · 이영희 · 박민수 · 최지우 · 정하늘. 사람당 한 번만 참/거짓을 판단하므로 경로 확장이 없습니다.

    07-6 · EXISTS 안에 조건 넣기: 2020년 이후 요리를 개발한 사람
    MATCH (사람:사람)
WHERE EXISTS {
  MATCH (사람)-[:개발]->(요리:요리)
  WHERE 요리.등록연도 >= 2020
}
RETURN 사람.이름 AS 요리사 ORDER BY 요리사;
    예상 결과

    박민수(비빔밥 2022) · 이영희(된장찌개 2021) · 정하늘(부대찌개 2020) · 최지우(라면 2023)

    STEP 08

    인덱스: 탐색 시작점 좁히기

    목표 인덱스가 없을 때와 있을 때의 실행 계획을 PROFILE로 비교합니다. 숫자는 환경마다 다르므로 직접 적어 가며 진행하세요.

    08-1 · 인덱스가 없는 상태에서 PROFILE
    PROFILE
MATCH (사람:사람 {이름:'김철수'})
RETURN 사람.이름;
    예상 결과

    결과 카드에서 실행 계획(Plan) 보기를 엽니다. 맨 아래 연산자가 **NodeByLabelScan**이고 그 위에 Filter가 있습니다. 사람 8명을 전부 훑은 뒤 이름을 비교했다는 뜻입니다. 맨 아래 연산자의 행 수(8)와 전체 DB Hits를 적어 두세요.

    08-2 · 인덱스 생성 — 노드 속성과 관계 속성
    CREATE INDEX 사람_이름 IF NOT EXISTS
  FOR (사람:사람) ON (사람.이름);
CREATE INDEX 요리_연도 IF NOT EXISTS
  FOR (요리:요리) ON (요리.등록연도);
CREATE INDEX 재료_분량 IF NOT EXISTS
  FOR ()-[관계:재료]-() ON (관계.분량);
    08-3 · 목록과 상태 확인
    SHOW INDEXES YIELD name, type, entityType, labelsOrTypes, properties, state
RETURN name, type, entityType, labelsOrTypes, properties, state
ORDER BY name;
    예상 결과

    사람_이름, 요리_연도(NODE), 재료_분량(RELATIONSHIP)이 RANGE · ONLINE으로 보입니다. 제약조건이 만든 요리_고유도 RANGE 인덱스이고, 데이터베이스가 기본으로 가진 LOOKUP 인덱스 2개도 함께 나옵니다. state가 POPULATING이면 잠시 뒤 다시 확인하세요.

    08-4 · 같은 질의를 다시 PROFILE
    PROFILE
MATCH (사람:사람 {이름:'김철수'})
RETURN 사람.이름;
    예상 결과

    맨 아래 연산자가 **NodeIndexSeek**로 바뀌고 행 수가 1이 됩니다. 08-1에서 적은 DB Hits와 비교해 보세요. 사람이 8명일 때는 차이가 작지만, 100만 명이면 100만 번 비교와 1번 도달의 차이가 됩니다.

    08-5 · 범위 조건도 RANGE 인덱스를 쓴다
    PROFILE
MATCH (요리:요리)
WHERE 요리.등록연도 >= 2020
RETURN 요리.요리명 AS 요리명, 요리.등록연도 AS 등록연도
ORDER BY 등록연도;
    예상 결과

    부대찌개 2020 · 된장찌개 2021 · 비빔밥 2022 · 라면 2023. 계획의 시작 연산자는 NodeIndexSeekByRange입니다.

    08-6 · 관계 속성 인덱스
    PROFILE
MATCH (출발)-[관계:재료]->(도착)
WHERE 관계.분량 >= 250
RETURN coalesce(출발.요리명, 출발.이름) AS 출발, 도착.이름 AS 재료, 관계.분량 AS 분량
ORDER BY 분량 DESC, 출발;
    예상 결과

    김치찌개 → 김치 300 · 떡볶이 → 떡 300 · 김치 → 배추 250. 계획에 DirectedRelationshipIndexSeekByRange가 보이면 관계 인덱스에서 출발한 것입니다.

    08-7 · 부분 일치에는 TEXT 인덱스
    CREATE TEXT INDEX 요리명_텍스트 IF NOT EXISTS
  FOR (요리:요리) ON (요리.요리명);
    08-8 · CONTAINS 질의
    PROFILE
MATCH (요리:요리)
WHERE 요리.요리명 CONTAINS '찌개'
RETURN 요리.요리명 AS 요리명 ORDER BY 요리명;
    예상 결과

    김치찌개 · 된장찌개 · 부대찌개. 인덱스가 방금 만들어져 아직 ONLINE이 아니면 스캔으로 실행될 수 있습니다. 잠시 뒤 다시 실행해 NodeIndexContainsScan이 나오는지 확인하세요.

    STEP 09

    제약조건: 데이터 품질의 최소 방어선

    목표 고유(Unique), 필수(Existence), 노드 키(Node Key) 제약조건을 만들고 잘못된 데이터가 저장 시점에 거부되는지 확인합니다.

    09-1 · 노드 키: (분류, 이름) 조합이 고유하고 둘 다 필수
    CREATE CONSTRAINT 재료_키 IF NOT EXISTS
  FOR (재료:재료) REQUIRE (재료.분류, 재료.이름) IS NODE KEY;
    09-2 · 필수 속성
    CREATE CONSTRAINT 사람_이름_필수 IF NOT EXISTS
  FOR (사람:사람) REQUIRE 사람.이름 IS NOT NULL;
    09-3 · 목록 확인
    SHOW CONSTRAINTS YIELD name, type, labelsOrTypes, properties
RETURN name, type, labelsOrTypes, properties
ORDER BY name;
    예상 결과

    3행: 사람_이름_필수(존재), 요리_고유(고유), 재료_키(노드 키).

    에디션 고유 제약조건은 Community 에디션부터 쓸 수 있고, 필수·노드 키 제약조건은 Enterprise 기능입니다. Aura는 Enterprise 기반이라 AuraDB Free에서도 실행되지만, Docker로 띄운 Community 이미지에서는 09-1과 09-2가 오류로 끝납니다. 그 경우 이 STEP의 09-4, 09-5, 09-7은 건너뛰세요.
    09-4 · 필수 속성 누락 (오류가 나는 것이 정상)
    CREATE (:재료 {이름: '소금'});
    09-5 · 조합 중복 (오류가 나는 것이 정상)
    CREATE (:재료 {분류: '가공', 이름: '김치'});
    09-6 · 고유 제약조건 위반 (오류가 나는 것이 정상)
    CREATE (:요리 {요리명: '김치찌개'});
    09-7 · 이름 없는 사람 (오류가 나는 것이 정상)
    CREATE (:사람 {나이: 30});
    예상 결과

    네 블록 모두 거부되고 데이터는 바뀌지 않습니다. 속성이 빠진 09-4 · 09-7은 22N77: … property presence verification failed, 값이 겹치는 09-5 · 09-6은 22N80: … index entry conflict 오류입니다.

    09-8 · 조합이 다르면 통과
    CREATE (재료:재료 {분류: '채소', 이름: '김치'})
RETURN 재료.분류 AS 분류, 재료.이름 AS 이름;
    예상 결과

    채소 · 김치 생성. 이름이 같아도 (분류, 이름) 조합이 다르면 허용됩니다. 확인 후 아래 블록으로 지웁니다.

    09-9 · 정리 (반드시 실행)
    MATCH (재료:재료 {분류: '채소', 이름: '김치'}) DELETE 재료;
    적재 전에 제약조건을 먼저 ① CREATE CONSTRAINT → ② MERGE · UNWIND 적재 순서가 중복 노드를 막는 가장 확실한 방법입니다. 이번 실습에서는 비교를 위해 사람 라벨만 일부러 순서를 바꿨습니다.
    STEP 10

    실행 계획 읽기와 튜닝 전후 비교

    목표 EXPLAIN과 PROFILE의 차이를 확인하고, 실행 계획을 아래에서 위로 읽은 다음, 개선 전 질의와 개선 후 질의의 DB Hits를 비교합니다.

    10-1 · EXPLAIN — 계획만 세우고 실행하지 않는다
    EXPLAIN
MATCH (n) DETACH DELETE n;
    예상 결과

    계획만 표시되고 데이터는 지워지지 않습니다. MATCH (n) RETURN count(n);으로 28개가 그대로인지 확인하세요. 위험한 질의는 EXPLAIN으로 먼저 점검합니다. (PROFILE을 붙이면 실제로 실행되므로 절대 바꿔 실행하지 마세요.)

    10-2 · PROFILE — 실행하며 잰다
    PROFILE
MATCH (사람:사람 {이름:'김철수'})
      -[:개발]->(요리:요리)
RETURN 요리.요리명;

    대량 갱신: 배치로 나눠 커밋

    목표 한 트랜잭션에 모든 변경을 담으면 메모리가 부족해집니다. CALL … IN TRANSACTIONS로 일정 행마다 커밋합니다. 데이터가 8건뿐이라 배치 크기를 3으로 줄여 동작만 확인합니다.

    11-1 · 정규화이름 채우기 — 3행마다 커밋
    :auto MATCH (사람:사람)
WHERE 사람.정규화이름 IS NULL
CALL (사람) {
  SET 사람.정규화이름 = trim(사람.이름)
} IN TRANSACTIONS OF 3 ROWS;
    예상 결과

    속성 8개 설정. 8행이 3 · 3 · 2로 나뉘어 세 번 커밋됩니다.

    :auto IN TRANSACTIONS는 질의가 스스로 트랜잭션을 여닫아야 해서, 화면이 미리 열어 둔 트랜잭션 안에서는 실행할 수 없습니다. 맨 앞의 :auto가 "자동 커밋으로 실행하라"는 화면 명령입니다. Aura Query 화면에서 :auto를 붙인 형태로 실행되는 것을 확인했습니다. 다른 도구에서 :auto를 인식하지 못한다는 오류가 나면 :auto를 지우고 MATCH부터 실행하세요.
    11-2 · 결과 확인
    MATCH (사람:사람)
RETURN count(사람.정규화이름) AS 채워진수, count(*) AS 전체;
    예상 결과

    8 · 8. 11-1을 다시 실행하면 IS NULL인 사람이 없어 아무것도 바뀌지 않습니다. 중간에 실패해도 처음부터 다시 실행하면 남은 것만 처리되는 구조입니다.

    11-3 · 실행 중인 트랜잭션 보기
    SHOW TRANSACTIONS YIELD transactionId, currentQuery, elapsedTime
RETURN transactionId, currentQuery, elapsedTime;
    예상 결과

    지금 실행한 SHOW TRANSACTIONS 자신이 한 행으로 보입니다. 오래 걸리는 배치 작업을 지켜보거나 멈춘 듯한 질의의 원인을 찾을 때 씁니다.

    배치 크기 실무에서는 1만~5만 행 사이에서 조정합니다. 너무 작으면 커밋 횟수가 늘고, 너무 크면 메모리 부담이 커집니다.

    Q5요리별로 직접 들어가는 재료의 분량 합계를 패턴 컴프리헨션과 reduce로 구하고, 합계가 0보다 큰 요리만 많은 순으로 출력하세요.

    정답 보기
    Q5 정답
    MATCH (요리:요리)

WITH 요리, reduce(합계 = 0, 분량 IN 분량들 | 합계 + 분량) AS 총분량
WHERE 총분량 > 0
RETURN 요리.요리명 AS 요리명, 총분량
ORDER BY 총분량 DESC;
